# H5 reliability contracts and acceptance recipes

Reusable engineering guidance, **not a platform specification or a shipped library**. Adopt only the selected work after inspecting existing code, save/economy rules and current official APIs. Do not replace a working architecture for uniformity. Project-specific IDs, slot names, limits, timeouts and historical pass counts are deliberately excluded.

## Identity, storage and cloud

- Unknown runtime identity may continue in isolated local scope, but must not write account cloud, boards or achievements. Network recovery is not identity confirmation. Keep platform account, archive UUID, local key, save lineage and request generation distinct.
- Guard the storage **getter**, reads and writes, including startup preferences. Separate in-memory play, verified local persistence and cloud success in the UI. Validate candidates before commit; retain a checksum-verified backup before migration/import/cloud replacement. Checksums detect corruption, not cheating. Future schema must not be overwritten by an older client.
- Native method existence is only a capability hint. Verify its actual synchronous/callback contract and a complete write/readback before relying on it. Enqueuing an asynchronous file write cannot satisfy a synchronous save transaction. Preserve original snapshots and identity on uncertainty; never silently initialize a fresh profile or claim a RAM-only session is durable.
- Classify reads as conclusively absent, present/valid, present/corrupt or unknown. Only an unambiguous documented missing result for the actual operation/path proves absence; generic `errMsg` text or a locally assigned “missing” category does not. Browser fallback requires validated owner/lineage and must preserve any known native save.
- Rewards and completion receipts are one persistence transaction. On save failure, rollback or retain a non-consumable confirmed-but-unsaved state with explicit recovery. Never show durable success solely because memory changed. A compatible mirror failing does not invalidate an already committed authoritative slot.
- Cloud startup is single-flight, with generation and settled-once checks after timeout/reset/account switch. Read failure is not empty cloud. Switching A → B with empty cloud must not upload A's local save into B. Preserve manual versus automatic sync product decisions.
- Reconcile only a provable sequence within the same lineage; back up before replacement. Use semantic equivalence only to decide whether a conflict chooser is needed, ignoring only proven display timestamps, equivalent default migrations or device preferences. Equal score/progress/collection totals do not prove equal saves: compare actual completed IDs, reward/ad receipts, streaks, event timing, active state and owner/lineage. Show concrete differing categories or values before long comparison cards. Keep separate strict snapshots and original remote tokens for stale-selection/write guards; semantic equality cannot authorize an overwrite. Bigger balances, newer timestamps or unrelated revisions are not sufficient, and unrelated resource balances must not be added or maxed.
- A successful upload callback is not verified remote content. Use returned archive IDs, then re-list/re-download and validate the exact operation receipt, owner and payload before saying “saved and checked.” Missing create acknowledgment or unknown outcome requires reread/reconciliation, not duplicate create or repeated settlement after taps/restarts.
- A message such as “another device updated the cloud save” may indicate only a sync-baseline conflict; the wording alone does not prove a second device or lost progress. Later level/progress growth proves subsequent progress, but without paired pre/post-exit snapshots and receipts it does not establish a permanent fix.
- A UI timeout/cancel invalidates local handling; an already issued remote write may still finish. Keep unknown-result state, reread before another write and avoid overlapping retries. Client preflight, leases or read-revision-then-write are not server CAS/atomic locks.
- Main saves and diagnostics sharing platform quota need one arbiter, main saves first; diagnostics may be dropped. Coalesce latest pending state and serialize at actual submission; classify failures and bound retry/backoff using verified current quota. Main reads must not depend on optional diagnostic/quota files. Disabling diagnostics does not erase legacy unknown-operation markers or relax main-save account/token/readback guards. TapTap read compatibility and guarded submission recovery are specified [in its platform reference](taptap.md#cloud-read-compatibility-and-upload-budget).

**Tests:** getter/read/write exceptions, declared-but-unusable native methods, callback-only writes at synchronous boundaries, explicit absence versus errMsg-only/unknown reads, quota exhaustion, inconsistent readback, corrupt primary/backup, future schema, old schema migration, alternating windows, reward save failure and refresh. For cloud: two real accounts/sessions/devices, empty/old/forked saves, equal totals with different payloads, stale selection after display-only changes, switch during request, missing create receipt, upload timeout followed by actual remote success, optional-file failure with readable main archive and diagnostics contention. Synthetic tests do not close real-account gates. Use isolated test saves.

### Cloud save queue and truthful status

Apply these requirements within the existing sync policy; they are not an implemented queue or proof that a source design is universally better. Keep the identity, conflict, strict snapshot, reward and unknown-write protections above.

- **Latest intent, separate attempt:** coalesce repeated saves into one account/lineage-scoped dirty intent and generation. After eligibility checks, generate current JSON at dispatch; freeze that attempt's snapshot/generation separately. A newer save during the request remains pending; an older completion must not mark it synced. Track local commit evidence separately from current memory and cloud generations. Retaining a provider or a successful RAM write does not prove local durability.
- **Bound waiting, preserve hard gates:** bound coalescing starvation from the first pending intent, rather than resetting the deadline on every action. Reaching that bound only makes work eligible for scheduling; verified platform quota, backoff, identity and reconciliation may defer it further. Manual/critical priority changes ordering or coalescing urgency, never bypasses hard rate limits. First create, replacement, retries and independent controllers need the same applicable budget; a client arbiter does not eliminate cross-device races.
- **Failure must not consume intent:** moving pending work into an in-flight attempt is not settlement. For a definitively failed attempt, retain/reconstitute the latest eligible intent and schedule bounded recovery even when no new save arrives; if a newer intent exists, keep it instead of restoring stale JSON over it. A backoff timestamp plus `finally` is insufficient when pending work was already cleared. Handle provider/serialization failure and early busy/throttle rejection too. On retry exhaustion, leave an honest pending/error state and a safe action. An unknown remote outcome blocks resubmission until reread/reconciliation; elapsed backoff is not proof of failure.
- **Suspend work, preserve progress:** background/switch cancellation must retain the authoritative local progress or explicitly identified volatile state and unsynced intent. Revalidate identity before rescheduling, check account/lineage/runtime generation at dispatch and after asynchronous stages, and invalidate stale providers/callbacks. Apply these gates to memory/cloud-only paths as well as normal autosave, manual saves and teardown. A canceled timer cannot cancel an issued remote write; preserve its unknown outcome. Do not rely on unload completion or promise that RAM survives exit.
- **Quiet, actionable waiting:** show queued/deferred as a normal nonblocking status, without a toast for each save or an endless spinner. Retain the last successful cloud operation time with its meaning (upload, readback or download verification), and expose a safe retry/reconcile/conflict action appropriate to the cause. Do not promise an exact completion countdown. Queue labels and recovery actions must reflect actual retained work; a failed local write must update the status rather than leaving a static “auto-save on” assurance.

Derive localized labels from evidence, not an enum name such as `synced`:

| Evidence/state | Truthful presentation and recovery |
| --- | --- |
| Current generation durably saved locally | “Saved on this device”; show cloud status independently. An earlier local commit does not cover newer memory changes. |
| Local write failed | “Could not save on this device”; retain recoverable state, distinguish rollback from unsaved memory, and offer the supported save recovery. Do not announce local success. |
| Memory-only / cloud-only with local storage unavailable | “Temporary progress” / “Local storage unavailable”; show which generation, if any, is confirmed in cloud. Until then, explain exit risk; cloud capability or a RAM save is not a cloud commit. |
| Unsupported / idle without queued work | “Cloud unavailable here” / “Not yet synced”; no permanent queued indicator or retry action that cannot work. |
| Queued or deferred | “Cloud backup queued” plus a reason when needed. Add “saved locally” only with durable evidence for the relevant generation. |
| Checking / downloading | Identify the read/check stage; neither means progress is uploading or saved. |
| Downloaded and validated | “Remote save checked”; this is a restore candidate subject to owner/lineage, full-save validation and conflict guards, not upload of the latest local progress. |
| Upload in progress / acknowledged | “Uploading” / “Upload acknowledged” for the captured generation. A callback alone is not readback verification. Newer dirty progress remains visible. |
| Readback verified / consistent | State exactly which generation/content was compared. Only validated matching owner, receipt and payload can establish checked sync; tuple/summary equality alone cannot. |
| Error / unknown outcome | Keep the last known success time, current durability and pending reason. Known failure may retry within budget; unknown outcome requires reconciliation first. |

Use the [queue/status acceptance matrix](../assets/validation-status.example.md#cloud-queue-and-status-acceptance--云队列与状态验收) for later implementations. Source-string assertions, delay arithmetic and mocked bundle checks do not establish end-to-end retry, current-generation labels or real-host/device acceptance.

## Offline progress, check-in and ads

These are distinct product contracts; do not add them merely because the target supports cloud or ads.

- Cold start and same-session foreground return share one offline settlement policy. Process each interval once using a high-water mark; cover rollback, repeated returns, midnight and caps. Preserve economy gates and the policy for discarded over-cap time.
- Where unclaimed rewards exist, keep separate time, money and ad ledgers: old unclaimed money must not freeze construction/time or erase new rewards. Direct-credit games need no artificial carried-money field. Ad-hidden time must not become duplicate offline progress; reset the frame clock on return.
- Check-in defines timezone, consecutive versus cumulative days, first-day eligibility and completion. Reward, claim flag and count commit together. Restoring older same-lineage saves retains anti-duplicate high-water marks without max/adding balances. A changed day boundary/activity version needs migration; daily tasks and ad quotas keep separate ledgers. Local clock guards are not trusted server time.
- Ads: verify eligibility → freeze target, reward and unique request ID → bind listeners and ensure loaded material → initiate display → validate documented completion for the original account/request/target → follow the [confirmation and credit contract](#reward-confirmation-and-recoverable-credit) → report saved success. Persisting a pending request before display is not proof of completion. Distinguish requests from display/recovery attempts; completion need not wait for the display Promise to resolve. Resettable daily counters cannot be unique IDs; duration, focus and timers are not completion evidence. Client deduplication is not distributed exactly-once. Use the [TapTap lifecycle and diagnosis recipe](taptap.md#rewarded-ad-lifecycle-and-missing-reward-diagnosis) for instance ownership, external jumps, ambiguous results, bounded recovery/logging and host-specific acceptance; do not transfer its callback shape to other platforms.

**Tests:** retained old receipt plus new interval, segmented versus whole settlement, repeated same-day ad attempts, pending target changes, duplicate/late callbacks, cancellation/no callback, pending/reward storage failure, refresh and audio recovery; day-boundary migration, old-save restore, rollback and cross-account isolation.

### Entitlement clocks, daily boundaries and legacy migration

**Hotfix experience, 2026-10-10:** source diffs, unit and isolated-browser receipts were inspected, with separate Owner feedback that two real accounts behaved normally after scanning a test entry. Apply only selected compatibility repair; do not expand rollback anti-cheat, add server time or introduce a new system. Preserve the target product's quotas, durations and timezone.

- **Sampling baseline:** an offset clock that retains an old `lastReal` while adding `lastReal - realNow` on every read repeatedly compensates one rollback and can push entitlement time far into the future. Advance adjacent-sample baselines and test repeated high-frequency reads after rollback and recovery; simulation deltas/test offsets do not drive entitlement wall time. Establish corruption only under demonstrated triggers, not that every save is broken. Daily boundaries must not permanently `max` a corrupted historical future time.
- **Migrate save and confirmation journal together:** load both and repair each day/time watermark so the journal cannot reinfect a corrected save. For selected repair where the product follows the current date, compare in the configured timezone: a different day resets its daily quotas; the same day retains used counts. Reconcile counts only within the same day/lineage where permitted. Preserve completed/confirmed sequences, credited tokens and pending credit; never clear reward history to repair dates. Save/journal failure, restart and duplicate callbacks retain the [recovery contract](#reward-confirmation-and-recoverable-credit) against duplicate credit for one entitlement.
- **Boosts and pending offers:** valid entitlements count down using actual device wall time instead of freezing behind an old future watermark. Expiry beyond the product's maximum remaining duration requires the approved restore/expiry migration; do not copy a case duration, subtract credited funds or create new free uses. Future-created or expired **unconfirmed offers** expire; confirmed unsaved rewards remain recoverable.
- **Separate time domains:** entitlement clocks, offline anchors and cloud-ordering metadata are distinct. Repairing a future `lastTick` must not manufacture offline money; preserve existing `pendingOffline` receipts. Handle `updatedAt`/`revision` under the existing cloud-ordering contract rather than rolling them back with entitlement time and making the repaired save appear stale. Never derive ad dates/boost time from a future metadata watermark, or mechanically max timestamps/revisions across lineages.
- **Refresh across the actual day boundary:** specify the product timezone; the verified case used Beijing midnight. Check at boot, save and ad request, and refresh quotas/buttons in a continuously open page without reload. Cash and income-boost quotas remain separate. Offline expansion belongs to its earnings receipt; free boosts do not prove an ad was watched. Derive each button's eligibility from its current receipt, not a uniform assumption for already settled or below-cap receipts.

**Migration acceptance:** read-only import of authorized real anonymized saves into an isolated environment, comparing funds, levels, construction/iterations, permanent multipliers and pending offline receipts. Do not upload originals or expose save contents. Cover boot, restart, several days later, exact boundary crossings, valid countdown, same-day usage, save/journal faults and one-time recovery after failure. Execute actual clocks, migration, ledgers and save code; SDK-ready mocks are isolated-browser conditions, not real ad rewards or cloud-write evidence.

**Evidence layers:** record Owner real-host QR feedback separately with account count and reported behavior; identifiers stay in protected project evidence. Without device models or per-ad traces, do not claim a complete Android/iOS matrix. Source test counts, builds and release status belong in local receipts rather than becoming this Skill's default results. Verify the reviewed candidate separately using [version-level status](taptap.md#build-identity-paths-and-version-level-release-state).

### Reward confirmation and recoverable credit

Apply to selected rewarded-ad work using the game's existing save and product contracts. Banner/interstitial lifecycle guidance does not create reward entitlements. These are engineering invariants to implement and test, not a claim that the Skill contains a tested runtime adapter.

- **Two deduplication scopes:** `requestId` suppresses duplicate callbacks for one request. A separate claim key binds account/save lineage plus run or settlement entity plus the **specific entitlement instance**. A new request cannot claim the same entitlement twice; a generic placement/offer type alone must not suppress a legitimately new claim. Freeze reward contents with that identity. Before offering another ad for that entitlement, handle any already confirmed unsaved reward.
- **Confirmation before durable credit:** where cross-refresh recovery is required, validate official completion and persist an immutable confirmation record first. Then commit the reward and its `creditedToken` as one authoritative save transaction/snapshot; only after successful commit clear the confirmation record. Request-pending, platform-confirmed and durably-credited are separate states. Local tokens/hashes are correlation or integrity data, not platform-signed receipts or server verification.
- **Retry without adding twice:** on game-save failure, preserve the confirmed entitlement and an explicit, non-consumable pending-save state. Retry from a trusted snapshot or an explicitly rolled-back state; do not add again to already mutated memory or require another ad. If save succeeded but ledger cleanup failed, restart detects the committed token and only clears the stale ledger entry. If the confirmation ledger also cannot be written, retain memory state and explain that closing the page can lose recovery; do not promise restart recovery.
- **Restore within the original scope:** load both the save and confirmation ledger before resuming credit. Old cloud/local restores must preserve or reconcile same-lineage credited high-water marks, otherwise a stale ledger can reissue spent rewards; do not merge account rewards or max/add resource balances. An uncertain lineage needs reconciliation, not blind replay. A full inventory or changed run/page must not silently discard an already confirmed entitlement or award it to the new context. Retain/route it according to an explicit existing product contract; do not invent a mailbox or server system to satisfy the example.

**Implementation acceptance:** execute the real adapter, timing, ledger and save layers while substituting only SDK, controlled clock and faulting storage. Cover same entitlement/new request; legitimate new entitlement; confirmation-ledger write failure; reward/token commit failure and same-page retry; committed save plus failed ledger cleanup; actual restart; old-cloud/local restore and retained claim watermarks; account/run changes and full inventory. Cover early completion and rejection after confirmation in the platform layer. A scenario list or isolated fake SDK test is not execution evidence; real-host lifecycle/completion and cross-device guarantees remain separate.

## Leaderboards

Freeze board ID, integer metric/range, encoding version, order, ties, overwrite/merge policy and eligibility. Do not coerce huge wealth into unsafe JS Number or encode hidden decimals without an agreed contract. Review/dev/imported-special saves require explicit eligibility. Unknown identity cannot submit.

Scope submission state by identity, save lineage and board namespace; changing board must permit its first submission. A successful callback confirms only the submitted snapshot, never a newer score queued during the request. Best-ever boards and current-state boards do not always merge with max. Invalidate old generations on account/save/board changes. Keep queued/syncing/synced/failed/range-limited/unsupported states truthful.

**Tests:** boundaries/illegal values, ties/increase/decrease, new board first submit, score changes during submission, never-returning callback, stale callbacks, retry, actual readback, nickname/avatar/self row. Opening a board is not a successful submission; client scores are not server authority or anti-cheat.

## Audio and settings

- One controller owns user intent, scene, background/ad interruption and actual playback state. Long BGM may use a reused native media element; short SFX may use WebAudio. Preserve a stable existing backend unless measurement justifies changing it. Encoded bitrate is not decoded PCM memory.
- First play happens directly within a user gesture. Fence stale play promises/resource events; autoplay rejection waits for another gesture. Unexpected stalls get bounded recovery, not endless new contexts/reloads. A loading `suspend` event is not proof of playback pause. Volume zero/muted, user pause and temporary ad ducking are different states.
- Fixed synthesized loops can be prerendered **from the project's own music** to decouple scheduling from rAF. Preserve loop tails and audition the seam. Dynamic composition, note interaction and rhythm timing need a different design; do not mandate one format/duration/sample rate.
- Loop clock wrap is progress. When testing main-thread blocking, read media time in a later event-loop task, account for wrap and record new synthesis nodes. Advancing clocks/running flags are not proof of audible uninterrupted sound. Diagnostics must not unlock audio and change the failure being observed.
- Separate music/SFX switches and volumes; persist preferences with failure handling. Specify whether cloud restore carries settings or device preferences win. Respect mute/pause on gesture, focus and ad return. Font scaling covers buttons/modals/canvas, long text and narrow screens at max size; font loading failure gets readable fallback. General font-family switching is not proven by a size control.
- Power-saving/motion settings change presentation only, not economy/simulation. Unsupported vibration degrades safely. Reset preferences, restart game, erase local save and erase cloud are distinct actions.

**Tests:** cold start, first gesture, switch scene/music, loop and seam, mute/zero, pause/restart/refresh, settings failure, play rejection/stall, stale promise, loading failure, ad success/cancel, background/lock/call interruptions, max-font narrow screen. Real iOS/Android host listening and long sessions remain separate from browser counters; one historical phone listening pass does not certify another game.

## Developer and Owner tools

Apply when developer/Owner controls are in scope; this is shared guidance, not proof of a game-side implementation. Put content unlocks, resource grants, speed changes, layer/level skips, instant test-ad rewards and diagnostic panels behind **Settings → Developer/Owner tools**. Do not leave persistent cheat buttons, banners, floating launchers or overlays on ordinary gameplay screens, especially over safe-area/capsule controls. Reuse the existing settings flow; the entry must remain reachable without a separate obstruction.

- **Build and save boundaries:** debug builds may retain these tools and isolated test saves. Production builds must not expose cheats or simulated ad-completion entry points, including hidden handlers reachable by URL/storage flags or shortcuts. Hiding a button alone is insufficient. Do not create a new cheat system for a game that has none. Preserve natural saves; manipulated test state must not enter ordinary cloud/leaderboard flows. Any selected non-cheating production support diagnostics stay in Settings and follow the bounded/redacted diagnostic contract.
- **Reward boundary:** label test rewards and simulation clearly. Keep test reward delivery separate from real SDK completion; it must not mark a real ad watched, consume real eligibility or change entitlement idempotency/settlement. Preserve the existing [reward contract](#reward-confirmation-and-recoverable-credit), including pending-save recovery. A debug shortcut is not platform reward evidence.
- **Pause and preferences:** opening/closing tools must compose with manual pause, ads and background lifecycle rather than force-resuming play/audio. Preserve existing mute, volume, speed and other preferences unless the Owner explicitly changes them. On close, remove modal pointer interception, stale overlays and listeners; restore the appropriate focus and prior pause state.

**Acceptance recipe:** on an actually measured narrow mobile viewport, inspect settled ordinary gameplay with tools closed: no debug strip/overlay, blocked buttons, intercepted taps or safe-area/capsule collisions. Open Settings, reach the tools, perform an authorized isolated test, close them and continue normal play. Cover long labels/max text, repeated open/close, manual pause, background/return, ads, prior mute and unchanged preferences. Check the actual production artifact for absent cheat/simulation access and separate debug-save behavior; a development screenshot or source flag alone does not prove production exclusion. Record build/version, actual viewport, settings route and evidence in the [validation record](../assets/validation-status.example.md). Report instruction-only updates separately from project implementation and executed browser/host/device results.

## Startup, layout, performance and diagnostics

An independent minimal HTML boundary covers module download/parse, sync/async initialization and timeout; show build/error code and retry by reload without clearing saves. Retire guards once usable UI or cloud preflight exists. Build target does not polyfill every DOM/Intl/storage API. Test same-origin HTTP builds; opening development source with file:// is not a player-device failure diagnosis.

Use one coordinate contract for viewport, DPR, render scale, safe insets and input inverse transforms; don't multiply DPR twice or paste Maker NanoVG calls into DOM/canvas code. Capture a consistent event snapshot; for host origins and notch/capsule handling, follow the [safe-area contract](#safe-areas-host-origins-and-capsule-placement). Test narrow/tall/tablet layouts, safe areas, max text, rotation and actual pointer/touch hit areas. Duplicate input suppression and reward idempotency are separate; verify runtime synthetic events rather than relying on arbitrary debounce timers.

Measure fresh, middle and advanced saves. Separate JS/layout/paint/input from product pacing. Reduce duplicate models, DOM measurements/writes and layout reads first; cache display calculations but revalidate purchases against current state. Presentation throttling/scroll quiet windows must preserve simulation, saving and full structure resynchronization. In the **same page instance**, test first unlock → stage transition → reset/rebirth → reappearing controls → late game. Refreshing between every stage can hide stale hidden-state bugs. Avoid universal frame-rate prescriptions or claiming a device root cause from an FPS screenshot.

Keep separate diagnostic cloud archives disabled by default. Preserve bounded local collection/copy and explicitly authorized host/MCP feedback; disabling cloud diagnostics does not disable unrelated HTTP analytics. Gate disabled entry points before payload serialization or SDK/filesystem access, even for cyclic/oversized inputs; skip startup controller construction/subscriptions and queued work that would list/read/write/create/update diagnostic archives. Leave old diagnostic archives and unknown-operation markers intact. This stop removes that traffic, not every cloud failure or cross-device risk.

If explicitly re-enabled, diagnostics remains an optional side channel with an independent schema/slot excluded from game restore and platform-assigned UUIDs. Apply a field allowlist, bounded strings/counters and final UTF-8 wrapped-byte limit. Keep build/stage, available host/device fields, numeric codes, callback field types and fixed error categories; wrappers must preserve the failing read versus quota/write stage and whether a numeric code was absent. Do not record raw SDK objects, local paths, UID, save body, tokens, signed URLs, arbitrary exception payloads or unbounded logs. Missing fields stay absent. Follow the shared-budget rule above; failure must not block gameplay. Document purpose/access/retention in the game. Do not promise a diagnostic upload every boot or capture before module startup/after OS termination.

**Tests:** missing APIs/modules/resources, storage failure before entry, sync/async throw, recover without erasure; actual layout/input and same-instance lifecycle; multibyte/emoji payload bounds, serialization/file-write errors, SDK no callback, shared quota, account switch, first-create race, disabled diagnostics with zero SDK/filesystem calls (including cyclic/oversized input), preserved legacy pending state and diagnostics failure without gameplay regression.

### Safe areas, host origins and capsule placement

Use this contract for selected layout work; it is guidance, not a supplied runtime adapter. Separate screen-relative native safe areas, the native window/WebView rectangle, CSS layout viewport, `visualViewport` and host capsule overlays. Validate finite dimensions, rectangle order, units, orientation and one coherent geometry snapshot before combining them. Derive native-to-CSS scale from matching window dimensions; do not multiply DPR again. Keyboard/zoom changes to `visualViewport` do not automatically describe a changed native window.

For valid portrait geometry in one native coordinate system, convert only the obstruction **remaining inside the window**:

```text
nativeTop    = max(0, safeArea.top - screenTop) * scaleY
nativeBottom = max(0, screenTop + windowHeight - safeArea.bottom) * scaleY
```

If CSS `env(safe-area-inset-*)` still describes the same screen inset, remove only its known, already-consumed native portion before taking `max(nativeRemaining, cssRemaining)`. Do not blindly add both sources, subtract consumption twice, or reuse portrait coordinates in landscape. Where the native origin is known but `safeArea` is absent, account for that origin when reducing an eligible fallback too. Unknown origin/geometry stays unknown; it is not a measured zero. Horizontal/inset-window geometry needs its own documented origin and transform.

- **Fallback scope:** prefer valid native/CSS measurements. Missing, throwing or zero data alone neither proves no obstruction nor authorizes a notch allowance on every host. Require positive device/platform identification, current native host and orientation, with a bounded project-configured fallback only for the demonstrated gap. Restricted UA or unknown model is not positive identification; keep working Android, classic-iPhone, tablet, landscape and browser paths intact. Do not invent bottom space to accompany a top-only fallback.
- **Capsule placement:** keep important actions out of the actual upper-right overlay using local header/action layout. Do not shrink every screen or scroll region by an extra vertical toolbar merely to protect that corner. Reserve the app rectangle for actual system/host insets; inspect long titles, modals and close buttons against the local capsule region.
- **Lifecycle:** tolerate absent, throwing and unusable APIs. Cache basic device identity per host binding; invalidate it on host replacement. Optional asynchronous results need viewport/host generation and disposal guards. Refresh geometry on relevant window/orientation/foreground changes without blocking play or accumulating listeners. Keep diagnostics bounded and geometry-only; exclude raw UA, player identity, credentials and business telemetry.

**Bounded case, inspected 2026-10-16:** blanket portrait padding first caused excessive empty space. Removing it preserved Owner-accepted Android spacing but exposed iPhone top occlusion. A later candidate used a **64 CSS px** top fallback for a positively identified portrait iPhone/iOS native host with a **long/short screen ratio ≥2**, and a **100 CSS px** local header capsule reserve. These are that project's heuristic and layout choices, **not official TapTap dimensions or universal defaults**. Feedback lacked native geometry, so missing/incorrect measurement remains a hypothesis. The later iPhone fix had dependency-fixture coverage, not native iPhone acceptance; its desktop landscape smoke test did not verify the portrait fallback.

**Regression recipe — execute against the target's real layout/runtime:**

| Case | Observable outcome / evidence |
| --- | --- |
| No-notch Android, classic iPhone, iPad, desktop and landscape | Known-good spacing stays intact; no unrelated phone fallback. |
| Measured iPhone; CSS and native insets both present | Insets apply once; key controls and scroll bounds remain usable. |
| Absent/throwing/zero geometry; restricted UA or unknown native identity | Only an explicitly eligible fallback applies; otherwise report the unverified case. |
| Full/partially inset window, including known origin without `safeArea` | Already-consumed top/bottom is not reserved twice; partial origin reduces the eligible fallback. |
| Late identity/geometry, host replacement, resize/foreground and disposal | Stale callbacks cannot restore old padding; listeners are cleaned up. |

Record **actual** `innerWidth/innerHeight`, relevant `visualViewport` dimensions/offsets and final app/header/control rectangles after the page settles. Nominal scenario names or inactive-tab resize requests are not viewport evidence; transition frames are not a visual pass. Native screenshots may omit the physical notch: pair them with geometry and Owner observation. Respect denied browser/device actions without another-route retries. Keep unit fixtures, browser layout, native SDK, real device and Owner acceptance separate. A feedback's processed flag is triage, not proof of repair; public testing is not formal release, and its uploaded artifact needs an independent version/hash mapping. Use the [validation record](../assets/validation-status.example.md).

## H5 upload and publication authorization

Apply current Owner instructions and actual tool side effects, not a blanket confirmation rule. Under the Owner policy updated **2026-10-16**, an authorized `taptap-cli` **upload-only** task does not require a second confirmation for every ZIP/build, including first uploads, development tests, hotfixes and reuploads. This does not create authority for unrelated uploads. Other channels/tools remain subject to their actual task authorization and applicable tool requirements; do not infer the CLI exception or an extra universal approval gate for them.

Before upload, finish necessary local checks and record target platform/`app_id`, exact path, version/SHA-256 (or a build manifest/hash), purpose and the command's actual effects. For authorized CLI upload-only work these are execution checks and delivery evidence, **not another approval step**. Verify upload/package/version state afterward. An unknown result requires read-only inspection before any repeat, not an automatic retry.

Before a `minigame-mcp` / `taptap-minigame` **publication operation**, including a combined call that may automatically submit for review, publish or overwrite the online version, disclose the specific target, artifact version/SHA-256, action and impact and obtain explicit Owner confirmation for that action. Changed artifacts, targets or repeated publication actions need fresh confirmation. Recheck the selected MCP app immediately before mutation and stop on mismatch. Read-only preparation is not publication authorization.

The CLI upload exception does not authorize main-package binding, review submission, publication, withdrawal, takedown, rollback or platform configuration changes; each needs its own applicable authorization. A combined CLI command is not upload-only and cannot extend the exception. If the Owner asks for upload without the release workflow, stop after upload and status readback. Do not substitute a browser, script, API or permissive setting to bypass required publication confirmation. For TapTap's observed coupled MCP route, apply the [automatic-review impact boundary](taptap.md#automatic-review-and-publication-impact); later withdrawal does not authorize an earlier submission.
