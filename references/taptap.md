# TapTap H5 target

Reviewed **2026-10-03** against the official [H5 MCP setup](https://developer.taptap.cn/minigameapidoc/quick-start/mcp-guide/mcp-setup/), [upstream MCP](https://github.com/taptap/instant-games-open-mcp) and enabled tool schemas. Refresh before use. This is the H5 route with host-injected global `tap`; ordinary browsers may lack it. Maker/UrhoX and native Android/iOS/Unity SDKs are different products.

## Prepare locally

Accept generic H5, TapTap H5 or another platform H5 baseline. Follow [selection](selection.md) before creating outputs. For a new TapTap target, isolate platform hooks and saves in an independent project. For an existing TapTap target, perform a three-way update and retain established keys, schema, reward receipts, app binding and old packages. Do not infer app ownership from a directory name.

Keep a runnable static build with `index.html`, relative resources and correct orientation. **Manual ZIP upload and MCP build-directory upload have different input contracts.** Prepare the selected route below and retain a checksummed game ZIP as a local candidate. Static success does not prove injected APIs or account binding.

TapTap listing rules remain pending current creator-form verification. Prepare truthful name, description, controls, icon/cover and gameplay images when selected; `assets/material-rules.json` intentionally imposes no invented TapTap dimensions/counts. Its warnings mean the kit is not certified complete. Verify current required fields, orientation, sizes and video scope before delivery; video remains opt-in.

## Manual ZIP layout and size

The **TapTap H5 manual-upload form reported by the Owner on 2026-10-06** requires ZIP only, at most 300 MB, with exactly one extracted top-level folder containing `index.html` directly. A flat archive was rejected at the same console for having seven root entries. This is field evidence for the manual ZIP route; recheck the current form at use time.

The shared `assets/package-rules.json` identifies this route as `manual_zip` and conservatively records **300,000,000 bytes** using decimal MB, measured against the actual ZIP file. Replace `game/` below with the game's folder name:

```text
game.zip
└── game/
    ├── index.html
    ├── assets/
    └── audio/
```

Place verified build contents inside one clean game folder, then archive **the entire folder**, not its selected contents flattened into the ZIP root. `index.html` must be directly inside that sole top-level folder, neither at the archive root nor one wrapper deeper. The ZIP root must not contain a README, a second folder (including an empty one), or any other file. Exclude `.DS_Store`, `__MACOSX`, development-only project files, credentials and tests; keep JavaScript and assets needed at runtime. Exclude traversal or absolute paths and symlinks. Preserve old packages and run both checks on the new candidate:

```sh
python3 <skill-dir>/scripts/verify_game_package.py <game.zip> --channel taptap --report <new-preflight.json>
python3 <skill-dir>/scripts/check_package_budget.py <game.zip> --channels taptap --stage candidate --report <new-budget.json>
```

On Windows use the verified `py -3` or `python` interpreter and quote real paths. Preflight rejects invalid layout and excess bytes; the budget report shows measured bytes, the limit and resource contributors. Both checks are local and read-only, with no upload.

**MCP route:** the current tool accepts a verified **build directory**, not arbitrary source or a listing ZIP. Inspect the current `prepare_h5_upload` / `upload_h5_game` schema for its directory entry contract and generated ZIP layout. Do not mechanically add the manual ZIP wrapper to MCP input or infer MCP limits from the manual route. The TapTap entry in the budget registry and `verify_game_package.py --channel taptap` currently cover manual ZIP candidates, not MCP directories or internally generated artifacts. Preserve the separate root-level `index.html` rules for 233/4399.

## Two-stage integration and release boundary

Device automation is opt-in: use [Android-device automation](android-taptap-automation.md) only when explicitly requested, including its startup confirmation. Missing images and CDN subpaths use [deployed-resource diagnosis](deployed-assets.md); ordinary integration does not occupy a device or install tooling.

Use this backend sequence confirmed by the maintainer on **2026-10-06**: **create the app → integrate selected non-ad features → build the first local package → obtain per-artifact confirmation and upload → set backend orientation → verify and integrate ads through MCP → rebuild the candidate**. Start when local development is approximately 90% complete and the core flow runs; the percentage is a handoff point, not acceptance evidence. The current `get_ads_integration_workflow` separately confirms active monetization, orientation and a valid space ID as code-generation prerequisites. Follow this first-package sequence and verify actual backend behavior for the project.

**Never publish an app to enable or integrate ads.** Publishing may complete review and expose the app immediately; do not assume a manual-review buffer. Track app creation, first upload, orientation, ad configuration, review submission and publication separately. Integration authorization does not include review submission or publication. Missing materials cannot be handled by publishing first and filling them later. If an MCP response or console suggests publishing, stop before that action and report the conflict; do not click publish, invoke an equivalent API or bypass the boundary with a combined tool. Continue independent local work. Formal review/release waits for required materials, relevant acceptance and explicit Owner authorization.

### Stage one: integrate non-ad features and build the first package

1. Verify the source, target `app_id`, existing project and [selected capabilities](selection.md). Once the backend app exists, verify the MCP application as described below. If it does not exist, provide creation materials and create only within actual authorization or let the Owner do so; do not publish.
2. Use the corresponding MCP guides to implement **selected non-ad features with a currently verified H5 route**, such as identity, cloud saves, leaderboards, sharing and vibration. Preserve product rules, saves and app binding. “All except ads” is not a requirement to add every feature; leave unverified capabilities pending rather than inventing APIs.
3. Keep newly requested ads unconfigured, with hidden or clearly unavailable controls. Never use sample space IDs or mock reward completion, and keep ordinary gameplay independent of ad setup. Preserve working ads in incremental updates rather than removing them to imitate a first-package flow. Build for the actual orientation; check `index.html`, resources, critical behavior and saves, then produce a local candidate ZIP with version, size and SHA-256. If MCP accepts a build directory, freeze its manifest/hashes and record its relationship to that ZIP.
4. Record completed features, the first package, missing materials and pending ads in existing delivery notes. Before upload, follow [per-artifact Owner confirmation](h5-reliability.md#h5-external-upload-confirmation): disclose the target, artifact, purpose and possible automatic review/publication/overwrite, then wait for explicit confirmation. An unknown impact cannot be called safe because this is a test build. If a tool cannot separate upload from automatic review/publication, default to stopping that route and apply the [impact gate](#automatic-review-and-publication-impact). For an unknown upload result, inspect read-only rather than retrying or publishing as a workaround.

### Stage two: confirm orientation after upload, then integrate ads

1. Verify a successful first-package upload for the same app. Set landscape/portrait in the backend, save it and verify the actual value matches the game. Reuse an explicit Owner choice. If using MCP `update_app_info` with `screenOrientation`, check the current schema and authorization for that change; modify only orientation without a publication action.
2. Follow the current `get_ads_integration_workflow`, verify the app and call `check_ads_status`. Only `status === 1`, correct orientation and a valid space ID automatically matched by this query permit `get_ad_integration_guide` and the selected ad integration. Never enter a space ID manually. Inactive/banned ads, missing orientation or server configuration errors block ad integration only; follow the reported recovery reason without publishing to unlock ads or automatically polling.
3. Apply this page's lifecycle and reward contracts, verify and rebuild the candidate with ads. Uploading that new package requires fresh per-artifact Owner confirmation; the first upload's confirmation does not cover it. Host playback, device checks, materials, review and public release remain separate states, pending wherever evidence is absent.

For an existing TapTap project, inspect first-upload records, orientation, ad status and existing integration read-only, and reuse satisfied steps. Never reupload or publish just to create another “first package.” If ads were not selected, finish selected non-ad work and local delivery without forcing the ad stage.

## Automatic review and publication impact

On **2026-10-10**, project evidence recorded `upload_h5_game` actually entering review, with a backend “publish immediately after approval” setting. Treat review submission as a dangerous external action: explain before execution that it may enter review and approval may make the app public. An upload-success message, refresh or reassuring status label does not establish safety or cancel review. This is observed behavior of that route, not a guarantee about every tool version.

When upload cannot be separated from automatic review/publication, **default to not using that route**. First deliver a concrete, reviewable plan identifying target/app, artifact path/version/SHA-256, purpose, current release setting, automatic review/publication/overwrite effects and available alternatives. Execute only after the Owner explicitly confirms that artifact/action including those effects. Device-flow startup consent and generic/previous upload approval do not cover it. Never perform an unapproved review submission intending to cancel it afterward.

Withdrawal requires its own explicit authorization and fresh verification of the actual review/public state afterward; cancellation is not guaranteed to beat approval. Rediscover current tools. If no withdrawal tool is exposed, state that limitation and describe authorized backend UI as a possible supplement, not a promised capability or automatic fallback. Preserve the separate prohibition on publishing merely to enable ads.

## Rewarded-ad lifecycle and missing-reward diagnosis

Reviewed **2026-10-06**: official [rewarded-video guide](https://developer.taptap.cn/minigameapidoc/dev/tutorial/open-capabilities/ad/rewarded-video-ad/), [creation API](https://developer.taptap.cn/minigameapidoc/dev/api/ad/tap.createRewardedVideoAd/), [close callback](https://developer.taptap.cn/minigameapidoc/dev/api/ad/RewardedVideoAd.onClose/) and [destroy API](https://developer.taptap.cn/minigameapidoc/dev/api/ad/RewardedVideoAd.destroy/). They establish automatic loading, readiness checks, recovery after display failure, boolean `isEnded`, default singleton behavior and optional `multiton: true`. The guide describes the default singleton; the creation API documents the multi-instance option. The transaction, event-order, timeout and diagnostic policies below are engineering recommendations requiring target-project tests; they are not additional SDK guarantees. Apply only to H5/Minigame global `tap`, never Maker/UrhoX callbacks.

1. **Load and show:** bind load/error/close listeners before display and ensure material readiness. Await `load()` or reuse confirmed loaded material; automatic loading means an extra load is not mandatory every time. After an explicit recoverable show failure, allow at most one `load → show` recovery per reward request. Merge `onError` and Promise rejection for the same failure into one transition and one recovery budget. A request stuck at `show.begin` without a result is unknown, not permission to open another ad concurrently.
2. **Ownership:** a unified manager maintains one active reward request. Keep a stable default shared-instance design, or use `multiton: true` for a request-owned instance when appropriate; multiple instances do not authorize concurrent ads. `requestId` correlates a request and its callbacks; `attemptId` identifies its display/recovery attempt. Neither replaces the separate entitlement claim key in the [reward contract](h5-reliability.md#reward-confirmation-and-recoverable-credit). Local IDs do not imply SDK callbacks carry IDs. If the old request has not definitively settled, do not hand the shared instance to a new request and assign its next `onClose` to that request. Isolate stale events using verified instance/listener lifecycle semantics. Remove the exact owned listener functions and timers; destroy only an exclusively owned instance, never another entry point's shared instance. Creating again does not by itself confer ownership. Both routes retain the current-app/MCP ad-configuration checks above.
3. **External jumps and cancellation:** hiding or leaving for an external app is not cancellation; retain the instance and listeners. Verify available platform lifecycle events because some hosts do not change `document.hidden`; normalize and deduplicate platform/DOM transitions. Pause the foreground waiting budget while backgrounded, configure a return grace period, and keep a separate overall expiry policy and usable cancellation/recovery entry. Return resumes the original wait, not reward credit or another display. UI cancellation/timeout does not close or cancel the host ad. After explicit cancellation, termination, account or target change, late callbacks cannot reward a new request; already confirmed entitlements follow the recovery contract. Restore usable UI without pretending an unresolved host operation has ended; do not wait indefinitely or overlap requests.
4. **Reward eligibility and event order:** accept only `onClose` with boolean `isEnded === true` for the still-valid original request, identity and reward target; false, missing values and string `"true"` are not success. Once display has been initiated and callback ownership is valid, completion may confirm the reward while `show()` is still pending. Do not gate it on a `shown` flag set only in `show().then(...)`. A later resolve/reject/error cannot replay an ad or reverse confirmed credit. Test these orderings without presenting them as an official ordering guarantee. A fulfilled `show()`, external-app activity, an ad's “reward received” message, returning to the game or elapsed watch time is not a reward receipt; do not add a local minimum watch-time test to a valid official completion. If no successful terminal event ever arrives, improve waiting/recovery and evidence collection; do not auto-compensate or claim the platform root cause is fixed.
5. **Persistence:** confirmation is distinct from saved credit. Follow the [confirmation ledger and entitlement contract](h5-reliability.md#reward-confirmation-and-recoverable-credit) for cross-refresh recovery, save retry and old-save reconciliation. Never require another ad merely to retry saving an already confirmed reward. Cloud list/download/file-read/create/update have separate outcomes; failed reads are not empty archives and must not clear local progress. If rewards and progress occupy different storage entities, verify each entity's commit and restoration. See [storage contracts](h5-reliability.md#identity-storage-and-cloud).
6. **Bounded diagnostics:** record create, load begin/result, show begin/result, hide/return, close/completion flag, reward validation/deduplication, local-save and cloud stages, with buildId, available host version, request/attempt IDs and timestamps/durations. These IDs must not embed account identifiers. Allow only available `errCode`/`errno`/`errMsg` fields; truncate and redact free text. Never dump SDK objects, tokens, signed URLs or saves. Optional JSON export/copy-recent-diagnostics uses fixed event and byte limits, with host support and failure feedback tested; export does not mean unlimited raw logs.

Distinguish `show.begin` from confirmed display in diagnostics. Also record bounded `reward.confirmed`, confirmation-ledger write, reward/save commit and ledger-cleanup outcomes; do not log full confirmation payloads or account-bearing claim keys.

**Minimum acceptance:** failed loading; explicit show failure with one recovery; show with no terminal result; error-event plus Promise double reporting; completion before show resolves; rejection after confirmation without replay/reversal; full viewing and early close; external jump/return including hosts with unchanged `document.hidden`; duplicate lifecycle notifications; foreground timeout and explicit cancellation; old close callback at the next-request boundary; shared and exclusively owned instance cleanup; account/target change; and the [reward persistence cases](h5-reliability.md#reward-confirmation-and-recoverable-credit). Match the tested build, device/host version and bounded logs. Execute the actual adapter, timer layer, ledger and save code, replacing only external SDK, clock and faulting storage. Test local and cloud persistence separately; a written matrix is not an executed test result.

**Evidence boundary:** an anecdote that explicitly loading restored playback, without a matching build, original logs and device result, is project feedback pending corroboration. It cannot prove that every show stall is caused by missing load, or that the recipe has passed on every host.

The ad protocol reviewed on 2026-10-06 supplied documents, not implementation, original logs or executed tests; its verified-case claim remains a source assertion. That source's 20-second pre-display budget, 120-second post-display budget, at-least-15-second return grace and 10-minute overall limit are case parameters, not Skill defaults or official promises. No source Agent metadata or invocation policy is adopted. Actual hotfix diffs and receipts were separately inspected on 2026-10-10; clock/day/legacy-save lessons are in [entitlement-time migration](h5-reliability.md#entitlement-clocks-daily-boundaries-and-legacy-migration), with unit, browser and Owner-host feedback kept separate from real ad/cloud-write acceptance.

## Build identity, paths and version-level release state

**Hotfix-receipt experience, 2026-10-10:** MCP uploads a build directory by creating its own archive and may combine review submission with release after approval; retain the [automatic-review gate](#automatic-review-and-publication-impact). A manually created ZIP matching directory contents proves only local correspondence. Its SHA-256 is not the MCP transport-ZIP hash. Record directory manifests, manual ZIPs, tool receipts and platform-version associations separately.

The currently discovered `prepare_h5_upload` schema requires a relative `gamePath`; rediscover it at use time. Resolve against the **MCP's actual working directory**, not the current terminal cwd or an old project. Verify selected app, tool cwd, explicit build path and entry. Once preparation is confirmed read-only, compare its resolved **absolute directory** with the frozen candidate before artifact-specific upload confirmation. If the return lacks enough information, obtain read-only verification or stop at the gap; never guess, blindly pass an absolute path or probe paths by uploading. Recheck resolved paths/manifests immediately before upload.

Development-round suffixes are not a version ordering: a later round's `r1` can retain an earlier round's `r2` functionality. Do not infer regression from cross-round suffixes; compare actual `buildId`, packaged features/file hashes and upload receipts. Build labels, platform versions and backend package IDs are distinct.

After review activity, read **version-level** online and draft/review records and map them to this build. App-level “published” may refer to the older online package; an upload message saying “published successfully” may also say the new package is under review. When the older version is online and the new one is reviewing, report uploaded/submitted and awaiting review/release. A test QR or positive Owner behavior feedback does not prove the public version switched. The source's final receipt remained at this waiting stage, not a live-current or released-state guarantee.
